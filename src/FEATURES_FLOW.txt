SMARTLOCKER STORAGE - PROJECT FEATURES AND FLOW
================================================

Project
-------
SmartLockerStorage is an ESP32-based locker controller with a DWIN user
interface, fingerprint user access, QR/manual borrower identification, RFID
key returns, slot lock outputs, administration, and SD-card audit logs.

Build
-----
The PlatformIO project targets the ESP32 DevKit V4 / esp32dev board and uses
src/main.cpp as its application translation unit. Feature implementation
headers are included once by main.cpp so they share the project declarations
and state. Build from the project directory with:

  pio run

Hardware and pin assignments
-----------------------------
- ESP32 DevKit V4.
- DWIN DMG80480Y070_02NR: UART2, RX GPIO16, TX GPIO17, 115200 baud.
- R503 fingerprint sensor: UART1, RX GPIO26, TX GPIO27, 57600 baud.
- GM861S/B1 QR scanner: software serial RX GPIO32, TX GPIO33, 9600 baud.
- DS3231 RTC and three MCP23017 expanders: I2C SDA GPIO21, SCL GPIO22.
- RC522 RFID: shared SPI SCK GPIO18, MISO GPIO19, MOSI GPIO23, CS GPIO5,
  reset GPIO4.
- One microSD module only: shared SPI, chip select GPIO14.
- CH376S USB host: SPI chip select GPIO25, interrupt GPIO35, using the
  Ch376msc library. GPIO35 is input-only and has no internal pull-up; use an
  external pull-up for the active-low INT line if the module does not provide
  one.
- Active-high safety limit switch: GPIO34, external 10k pulldown to GND.
- 40 slot outputs are driven by three MCP23017 expanders at I2C addresses
  0x20, 0x21, and 0x22. HIGH activates/unlocks an output; LOW locks it.

No SD select or export-SD select is assigned to GPIO13 or GPIO15.

Startup and main loop
---------------------
1. setup() starts Serial, configures chip-select pins, starts I2C with a
   bounded 100 ms transaction timeout, then initializes the MCP23017
   expanders before SPI, DWIN, RTC, or other modules. It probes MCP addresses
   0x20, 0x21, and 0x22 sequentially and reports each result. For each detected
   MCP, the output latch is written LOW before its pins are configured as
   outputs.
2. The loading page reports MCP status, then initializes the RTC, single
   GPIO14 SD card, CH376S USB host, RFID, fingerprint, and QR scanner.
3. Maintenance settings, accounts, registered keys, admin PIN, transaction
   history, and available log dates are loaded from persistent storage.
4. Initialization failures are written to Serial with each module name and
   summarized before startup continues to Page 1 (Locked Screen). Optional
   QR and CH376S failures do not block startup. QR readiness means its serial
   interface started; scanner presence is only known after scan data arrives.
   CH376S runs an SPI CHECK_EXIST probe before library initialization, so an
   absent controller is reported and skipped rather than entering the
   library's interrupt-drain loop.
5. The readiness results are reported for diagnostics only. Slot selection,
   borrowing, and returns are not gated on SD, RTC, or RFID readiness. Each
   detected MCP23017 is initialized individually, but all three must be
   detected for normal slot output control. Firmware drives detected MCP
   outputs LOW as its earliest initialization action; external pull-downs are
   still required to keep driver inputs LOW during power-up before firmware
   can communicate with MCPs. Physical prototype testing confirmed the slot
   lock outputs now initialize and operate as intended.
6. loop() handles DWIN events, safety checks, RTC updates, USB status checks,
   idle sleep, fingerprint login on the Locked Screen, RFID return scans on
   the Locked Screen and both Home Dashboard pages, timed slot relocking, and
   QR input while Page 4 is active.

No module-failure or "feature unavailable" status has been added to the DWIN
interface. Module initialization results are reported through Serial only.

User access and borrowing
-------------------------
1. On Page 1, a fingerprint must match a sensor template linked to a saved
   account before the Home Dashboard opens. The account name becomes the
   current user for borrow records.
2. On Page 2 or 3, tapping an active, unoccupied slot selects it. Tapping that
   same slot again deselects it; tapping a different available slot moves the
   selection. This single-selection toggle works on both dashboards. The user
   confirms the selection to continue. Slot touch events are identified by
   their VP address; a value of 0x0000 is valid.
3. Page 4 listens for QR data when the QR serial interface is initialized.
   The scanner itself has no startup presence handshake, so a disconnected
   scanner does not block the page; the borrower name can still be entered
   manually with the on-screen keyboard. Scanned codes can optionally resolve
   through /students.csv.
   Pressing OK with no borrower name cancels the pending borrow, clears the
   slot selection, and returns to the dashboard.
4. Confirming a borrower first appends and verifies the transaction in the
   daily SD archive. If that commit fails, the borrow is cancelled and the
   slot state/output remain unchanged. After a successful daily commit, RAM
   logs/state and the slot output are updated. A failed monthly mirror is
   queued for periodic retry and rechecked against daily archives at startup.
5. The slot output automatically returns to the locked level after
   RETURN_UNLOCK_MS. The slot remains marked occupied until its registered
   RFID key is scanned on Page 1, 2, or 3.

RFID return flow
----------------
1. RFID returns are polled only on Home Dashboard Pages 2 and 3, not on the
   Locked Screen.
2. The scanned UID must match a registered key whose slot is currently marked
   taken. Unknown keys and keys for unoccupied slots do not change the locker.
3. The return transaction must first be appended and verified in the daily SD
   archive. If that commit fails, the return is cancelled and the slot remains
   borrowed/locked. After a successful daily commit, the slot is marked
   available in Preferences, its output is activated for RETURN_UNLOCK_MS,
   and the output is then relocked.
4. Current logs and transaction history receive the committed return record.
   Monthly archive mirrors are retried if needed. The auxiliary returns.csv
   row is also written; its failure is reported without undoing a return whose
   authoritative transaction row was already committed. Repeat scans of the
   same UID are rate-limited after a successful return.

Admin flow and pages
--------------------
- Admin buttons open Page 5, where the four-digit PIN is checked.
- The default PIN is 3030. A changed PIN is stored in ESP32 Preferences.
- Successful login opens Page 7. Account, registration, key registration,
  maintenance, and password-update page commands require an authenticated
  admin session. Returning to a user dashboard or the Locked Screen ends that
  session.
- Page 7 displays transaction rows and selectable dates. Page 8 displays
  accounts and links to registration and Page 27 password update.
- Page 9 enrolls a user by saving a name and enrolling a fingerprint twice.
- Page 10 associates a key name, slot number 1-40, and RFID UID.
- Pages 11/12 let an admin mark slots active or inactive; those settings are
  saved to ESP32 Preferences.
- The DWIN page and VP reference is in VP_VALUE_MAPPING.txt.

Persistent data and SD archive layout
-------------------------------------
The one SD card on GPIO14 stores both archive periods. Each event row is
written to a date folder and also mirrored into that month's folder:

  /daily/YYYY-MM-DD/accounts.csv
  /daily/YYYY-MM-DD/keys.csv
  /daily/YYYY-MM-DD/transactions.csv
  /daily/YYYY-MM-DD/returns.csv

  /monthly/YYYY-MM/accounts.csv
  /monthly/YYYY-MM/keys.csv
  /monthly/YYYY-MM/transactions.csv
  /monthly/YYYY-MM/returns.csv

The files are append-only CSVs. Text fields containing commas, quotes, or
line breaks are quoted and escaped. Transaction rows have these fields:
date,key number,borrower,key name,borrow time,return time,user.
Account, key-registration, and return rows retain their existing field
layouts. Transaction rows and date folders are read back on startup for the
Admin Dashboard. Current-log cards are rebuilt from the RTC day's transaction
archive during startup and when the RTC date changes. They therefore survive
a power cycle as long as SD writes succeeded and the same card is available.
The current-log display retains the newest 40 events for the active date.
The daily transactions.csv file is authoritative for borrow/return commits:
the firmware verifies the daily row before changing slot state or activating
an output. Monthly files are mirrors; failed mirror writes are queued for
periodic retry and missing rows are discovered from daily archives on startup.
Current-log cards and Admin Dashboard transaction rows are presented
newest-first; the CSV archive itself remains append-only and chronological.
The first visible card/row is the latest event, so recent activity is visible
without scrolling. Current-log scrolling moves toward older events. Transaction
scrolling can browse older/newer events; when a new event is logged while the
Admin Dashboard is showing today's date, the table returns to the latest row.
The selected date remains unchanged for USB export.

Existing root-level accounts.csv, keys.csv, transactions.csv, and returns.csv
are migrated into the matching daily and monthly folders on startup. The
legacy root file is removed only after all of its rows have been archived.
If migration fails, an error is logged and the source file is retained for a
later retry.

User accounts, registered keys, active/inactive slot settings, taken/available
slot state, and the admin PIN are saved in ESP32 Preferences. Fingerprint
templates remain in the sensor. The resetEverythingForActualProject()
function clears these records, known SD archives, and fingerprint templates;
its call in setup() is commented out and must remain so during normal use.

Student roster (optional)
-------------------------
Place /students.csv in the SD card root. Each row contains:

  student_code,student_name

The QR code's extracted borrower code is matched to the first column. A match
overrides the name extracted from QR text. If the file or code is not found,
the existing QR parser name or manual keyboard entry is used. The reset
routine does not delete /students.csv.

Safety and display idle
-----------------------
- GPIO34 is checked every LIMIT_SWITCH_CHECK_INTERVAL milliseconds. On an
  active edge, all slot outputs are locked and temporary selection/QR data is
  cleared; the UI returns to Page 1.
- Entering or leaving a dashboard clears stale slot selections. Dashboard
  slot/confirm touches are ignored while the safety switch is active. A DWIN
  slot touch is identified by its VP, so a returned data value of 0x0000 is
  accepted as a valid touch value.
- A dashboard slot touch toggles the selected slot off when that same
  available slot is tapped again. Tapping another available slot moves the
  single selection. This behavior is implemented for both Pages 2 and 3.
- After DISPLAY_IDLE_TIMEOUT_MS without user activity, unfinished input is
  cleared, the display returns to Page 1, and the DWIN backlight is turned off.
- A DWIN Return Key Code / Basic Touch object using VP 0x13F0 can provide a
  dedicated wake touch. The first touch while asleep wakes only the display.

USB download
----------------------------------------------
The CH376S is initialized with the Ch376msc library, detects insertion/removal
through its interrupt, and checks that the USB drive is mounted before export.
On the Admin Dashboard, select a date and press Download to copy the
non-empty daily CSV files from /daily/YYYY-MM-DD/ to the USB drive root:

  YYMMDDA.CSV - accounts
  YYMMDDK.CSV - key registrations
  YYMMDDT.CSV - transactions
  YYMMDDR.CSV - RFID returns

The actual filenames have no spaces (for example, 261019T.CSV). This short
8.3 naming format is used for CH376S compatibility. The YY date prefix means
files from the same month/day in different centuries could collide; the
project's current year range does not approach that limit. Existing matching
files on the USB drive are replaced. Missing and empty daily category files
are skipped. The DWIN status reports success only if at least one non-empty
archive was copied, all attempted copies completed, and each exported file's
USB size matches the corresponding SD source size.

The CH376S shares SPI pins with the SD card and RFID reader. Their chip-select
lines must remain inactive during another device's SPI operation. GPIO35 has
no ESP32 internal pull-up, so verify that the module provides a suitable
pull-up on INT; otherwise add an external pull-up compatible with the module's
logic voltage. Validate drive power and filesystem compatibility using the
module/library documentation and a known-good USB drive.

RTC setup
---------
To set a fixed DS3231 date/time once, set SET_RTC_FIXED_ONCE to 1, configure
the RTC_FIXED_* values in main.cpp, upload, then set the flag back to 0 and
upload again. If the RTC reports lost power, it is set to the compile time.
